## VPN DNS 优先改造验收进度

已确认原生分流的前提不成立：Rcs 授权资源和 `Dns.data` 静态映射不是完整 DNS 域名清单，存在未列出的目标仍可由 VPN DNS 解析。当前实现改为 VPN DNS 优先，不能用此前固定 53 端口或修改网络服务 DNS 的结果代替本次验收。

当前实现使用回环随机高端口上的同端口 UDP/TCP 监听，由辅助服务在 `SCDynamicStore` 发布 `SupplementalMatchDomains: [""]` 的临时 resolver，保留原 `SCNetworkPreferences`。静态映射未命中后按配置顺序查询全部服务端 DNS，单次预算八秒，不回退公共 DNS，不截获其他 DNS。更具体的既有 supplemental resolver 与 mDNS 按系统规则处理；DNS 查询经过 VPN 不改变业务授权路由。

厂商客户端支持首选 DNS 模式；`filter=(null)` 和 `DnsRuleExceptions` 的含义尚无充分证据，不据此宣称精确复刻厂商策略。

本次已在重新构建、签名并安装的正式核心上通过 Computer Use 和系统命令验证：

| 项目 | 结果 |
| --- | --- |
| 系统解析入口 | 临时 catch-all resolver 生效，使用回环随机高端口；网络服务原 DNS 偏好保持自动获取 |
| 域名覆盖 | 未出现在资源域名清单中的授权目标通过原生解析并返回 HTTP 200；无需手工补域名 |
| DNS 传输 | 私有监听端口上的 UDP 与 TCP 均返回有效 A 记录 |
| 公网访问与路由 | 公网测试页面返回 HTTP 200，默认业务路由仍使用物理网卡 |
| 关闭窗口 | 连接和三个进程保持，授权业务仍返回 HTTP 200 |
| App 异常结束 | 强制结束 UI 后，核心和辅助服务全部退出，临时 resolver 消失，DNS 与偏好恢复；再次启动可连接 |
| Cmd+Q | 重新连接后通过 Computer Use 退出，UI、核心、辅助服务全部退出；DNS、接口清单及 DNS 偏好与本次连接前基线完全一致 |

App 异常结束时的较早接口基线包含另一客户端的临时网卡，不能据此声称整份接口清单相等；最终 Cmd+Q 使用重新采集的干净基线验证。生产核心单独强制结束因进程权限未执行，仍待验证。既有更具体 supplemental resolver 和 mDNS 的选择只依据系统规则，尚未完成专门共存实测。

## 审查修复

已通过主代理与子代理交叉检查并修复：

- 握手部分失败泄漏已有连接，读写重连后没有实际重试。
- 传输协程异常退出不能统一释放，以及 DNS I/O 不能及时响应取消。
- DNS 授权域名映射缺失、动态路由和缓存可能持续增长。
- TUN 变化被当作物理出口变化，引发反复重连的风险。
- 核心最后失败事件与进程退出竞态，可能将认证错误误判为可重试退出。
- DNS 整字典比较误判冲突，以及网络配置锁无限等待阻塞停止流程。
- launchd 相对启动路径导致找不到正确的核心文件。
- 首次服务注册待批准时误报普通失败；服务未启动时退出可能被取消。
- 非 VPN 网页缺少必需登录字段导致越界崩溃。
- 旧凭据清理失败后，活动记录及后续连接请求没有同步到实际保存的新记录。
- 重复退出绕过等待，以及主动断开成功后仍保留 XPC、使辅助服务无法空闲退出。
- 将一条记录修改为另一条的相同地址和账号时，可能产生重复记录；现已在输入及保存边界明确拒绝。

## XPC 连接替换回调验证

旧连接的失效、打断和订阅回复回调在主线程执行前检查连接身份，只有仍为当前连接时才更新状态。临时 fixture 复用了正式 HelperClient 的连接建立、主动失效和异步 handler，移除签名绑定、resume 与远程订阅以隔离真实系统服务。修复前，旧 handler 排队后替换连接会将新连接清空；修复后，旧失效与打断回调均被忽略，新连接保留，当前连接的失效与打断回调仍正常执行。此结果证明回调归属修复，重新构建并安装后，实际 XPC 登录与连接成功，内网授权页面及公网测试页面均返回 HTTP 200；手动断开后的 DNS、接口清单和 DNS 偏好与连接前基线一致。

## 自动重连预算验证

复现了核心反复“就绪后立即退出”的场景：修复前，每次短暂成功都会清零次数，实际超过四次自动重试仍不停止。当前改为连续稳定连接至少 30 秒，离开已连接状态时才恢复预算；使用系统单调时钟，不增加定时器。

临时 fixture 复用正式 Controller，隔离存储与 Helper，仅加速重试延迟并注入时钟。短连秒退恰好执行首次连接加四次重试后停止；主动断开后不再尝试；29.999 秒未恢复预算，30 秒恢复；重复的同会话已连接事件不改变计时起点。断网、服务中断和唤醒触发路径均结算并清除稳定计时。fixture 验证通知处理路径，实际电脑睡眠唤醒仍待实测。正式构建实机手动断开并完成清理后，继续观察 20 秒，没有重新出现核心进程；随后通过 Computer Use 执行 Cmd+Q，确认 UI、辅助服务及核心均无残留。

## 资源测量进度

以下为先前正式连接构建的后台空闲基线，均统计 UI、辅助服务和核心三个进程，关闭主窗口后测量。两个口径分开采样，不混加。

| 指标 | 时长与采样 | 结果 | 限制 |
| --- | --- | --- | --- |
| RSS 总和 | 300 秒、61 次 | 平均 178.70 MB，范围 174.36—182.06 MB，CPU 约单核 0.09% | 共享页可能重复计算，不等于活动监视器的内存占用 |
| Physical footprint 总和 | 约 61 秒、11 次 | 约 66.08 MB，CPU 约单核 0.03% | 使用系统 top 的 mem 指标，显示值经过取整；不是逐字节精度 |

Physical footprint 采样末尾三个进程分别约 45.09、6.31、14.68 MB。系统 top 手册将 mem 定义为进程的 physical memory footprint；测量脚本增加 --metric footprint，RSS 仍为默认口径。

该空闲场景的 physical footprint 短时结果低于 100 MB；RSS 总和超过 100 MB。持续传输、长期增长、最新所有交互场景以及同条件 EasyConnect 对比仍待完成，不把此结果泛化为全部场景均低于 100 MB，也不以五分钟采样宣称不存在长期泄漏。

最新 VPN DNS 优先构建重新采样：真实连接、主窗口关闭，physical footprint 约 61.06 秒、11 次，三个进程合计平均 53.94 MB，范围 53.92—53.95 MB，CPU 约单核 0.11%。末次 UI、辅助服务、核心分别约 34.60、4.64、14.68 MB；top 显示值取整。该结果仅代表本次短时空闲场景，不能作为持续传输峰值或长期无增长的证据。

追加五分钟观察：DNS 优先构建（a08d259，早于本轮 XPC 与重试预算修复）真实连接并关闭窗口，采样 301.06 秒、20 次，三个进程 physical footprint 合计平均 47.85 MB，范围 47.58—52.82 MB，CPU 约单核 0.11%。采样结束时 UI、辅助服务、核心分别约 34.60、4.59、13.63 MB。该范围不能用于判断长期趋势，也不作为后续修复构建的五分钟测量结果。
